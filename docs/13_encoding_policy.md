# 인코딩 및 문서 작성 기준

## 1. 문서 개요

| 항목 | 내용 |
|---|---|
| 문서명 | 인코딩 및 문서 작성 기준 |
| 프로젝트명 | Ops Monitor |
| 작성 목적 | 한글 문서와 운영 화면이 깨지지 않도록 파일 인코딩과 표현 규칙을 통일 |
| 적용 범위 | 소스 코드, 테스트 코드, Markdown 문서, 설정 파일, 임시 산출물 관리 |

---

## 2. 왜 먼저 인코딩을 정리했는가

이번 정리는 단순히 글자가 깨져 보이는 현상을 고치는 작업이 아니다.

운영 도구 프로젝트에서 인코딩이 흐트러지면 아래 문제가 바로 생긴다.

- 대시보드 문구와 테스트 문자열이 환경마다 다르게 보일 수 있다.
- 문서가 한글 중심인데 터미널, 에디터, Git diff 결과가 제각각 해석될 수 있다.
- 면접이나 포트폴리오 제출 시 문서 신뢰도가 떨어진다.
- 장애 대응 문서에서 명령어 결과와 설명이 뒤섞여 읽기 어려워진다.

즉, 인코딩은 보기 좋은 수준의 정리 문제가 아니라 운영 기록의 일관성과 협업 안정성에 직접 연결된다.

---

## 3. 이번에 적용한 기준

### 3.1 파일 인코딩 기준

모든 주요 텍스트 파일은 `UTF-8`을 기준으로 유지한다.

| 파일 유형 | 기준 |
|---|---|
| Python 소스 | UTF-8, LF |
| Markdown 문서 | UTF-8, LF |
| YAML / JSON / HTML / CSS / JS / TXT | UTF-8, LF |
| 환경 예시 파일 | UTF-8, LF |

### 3.2 에디터 공통 규칙

루트에 `.editorconfig`를 추가해 아래 기준을 명시했다.

- `charset = utf-8`
- `end_of_line = lf`
- `insert_final_newline = true`
- `trim_trailing_whitespace = true`

이 규칙을 먼저 둔 이유는, 앞으로 문서를 아무리 정성껏 써도 저장 규칙이 제각각이면 다시 깨질 수 있기 때문이다.

## 4. 한글 문서 표현 기준

이 프로젝트의 문서는 모두 한국어 사용자를 기준으로 읽히도록 구성한다.

| 항목 | 기준 |
|---|---|
| 기본 언어 | 한국어 |
| 문서 제목 | 한국어 우선 |
| 설명 방식 | 결과만 적지 않고 이유와 선택 배경을 함께 기록 |
| README 역할 | 현황 보고서가 아니라 제품 소개서 |
| 운영 문서 역할 | 점검 절차, 판단 기준, 예외 상황까지 포함 |

영문 용어를 완전히 배제하지는 않는다. 다만 아래 원칙을 따른다.

- 업계에서 고유명사처럼 쓰이는 경우는 유지한다.
- 처음 등장할 때는 한국어 설명과 함께 적는다.
- 문서의 주제 문장과 결론은 한국어로 쓴다.

예:

- `readiness probe`: 준비 상태 확인 프로브
- `monitoring loop`: 주기 점검 루프
- `run report`: 실행 단위 리포트

---

## 5. 임시 산출물 관리 기준

작업 중 외부 글을 확인하기 위해 저장한 HTML, 임시 캡처, 분석용 텍스트는 프로젝트 핵심 산출물과 구분해야 한다.

이번 정리에서는 아래 기준을 적용했다.

| 항목 | 기준 |
|---|---|
| 외부 참고용 HTML | Git 추적 제외 |
| 실험성 캡처 | 필요 시 문서에서 목적을 설명한 뒤 유지 |
| 제품 설명 자산 | `docs/assets`에서 명시적으로 관리 |

이 기준을 둔 이유는 README와 문서 폴더가 “무엇을 보여주기 위한 저장소인지”를 흐리지 않기 위해서다.

---

## 6. 왜 `.editorconfig`를 선택했는가

인코딩 문제를 해결하는 방법은 여러 가지가 있다. 예를 들면 IDE 개인 설정에만 맡길 수도 있고, 팀 규칙만 문서로 적어둘 수도 있다.

하지만 이번 프로젝트에서는 `.editorconfig`를 선택했다.

선택 이유는 다음과 같다.

1. 저장소 자체에 규칙을 포함할 수 있다.
2. VS Code, JetBrains 계열, 여러 편집기에서 폭넓게 읽힌다.
3. 문서 규칙을 말로 설명하지 않아도 파일 수준에서 기준을 공유할 수 있다.
4. 코드와 문서가 같이 많은 프로젝트에서 유지 비용이 낮다.

즉, 가장 단순하면서 재발 방지 효과가 큰 도구라고 판단했다.

---

## 7. 앞으로의 운영 기준

이후 문서와 코드를 추가할 때는 아래 순서를 권장한다.

1. 새 파일을 만들 때 UTF-8 기준으로 저장한다.
2. 한글 문구가 포함된 테스트는 실제 렌더링 문자열과 같이 검증한다.
3. README는 제품 소개 관점, 세부 문서는 운영 관점으로 역할을 분리한다.
4. 임시 분석 파일은 Git 추적 대상에 올리지 않는다.

---

## 8. 기대 효과

이번 정리를 통해 기대하는 효과는 아래와 같다.

- 한글 README와 기술 문서가 환경에 덜 흔들린다.
- 대시보드 UI 문구와 테스트 문자열의 일관성이 좋아진다.
- 면접, 포트폴리오, 코드 리뷰에서 문서 신뢰도가 올라간다.
- 이후 체크 대상 추상화나 리포트 확장 작업을 할 때 문서 구조가 덜 흐트러진다.

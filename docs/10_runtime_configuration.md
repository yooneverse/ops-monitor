# 런타임 설정 가이드

## 개요

이 문서는 `ops-monitor`의 런타임 설정 검증, 운영 화면 노출 기준, 데모 서비스 상태 연동 기준을 함께 정리합니다.

목표는 단순합니다.

- 잘못된 모니터링 설정값이 들어와도 애플리케이션이 시작 단계에서 바로 깨지지 않을 것
- 보호된 모니터링 API에서 어떤 설정이 기본값으로 대체되었는지 확인할 수 있을 것
- 운영자가 `/dashboard`에서 임계치와 설정 상태를 바로 읽을 수 있을 것
- 운영자가 대시보드에서 부가 서비스 연결 여부까지 같이 볼 수 있을 것
- 운영자가 어떤 점검 대상이 제외되었는지 바로 알 수 있을 것
- 이벤트 로그와 별도로 점검 실행 1회 단위 결과를 복기할 수 있을 것

## 변경 내용

### 1. 정수 설정값 안전 검증

이제 핵심 숫자형 환경 변수를 사용하기 전에 범위를 검증합니다.

| 변수 | 기본값 | 허용 범위 | 잘못된 값일 때 동작 |
|---|---|---|---|
| `MONITOR_INTERVAL_SECONDS` | `30` | `5` ~ `3600` | `30`으로 대체 |
| `MEMORY_ALERT_THRESHOLD` | `80` | `1` ~ `100` | `80`으로 대체 |
| `DISK_ALERT_THRESHOLD` | `80` | `1` ~ `100` | `80`으로 대체 |

또한 `"   "`처럼 공백만 들어간 인증 정보는 `None`으로 정규화해서, 일부만 채워진 유효하지 않은 값처럼 취급되지 않도록 했습니다.

### 2. 모니터링 상태 응답에 설정 메타데이터 추가

`GET /monitoring/status`는 이제 아래 정보를 함께 반환합니다.

- `monitor_auth_configured`
- `api_docs_enabled`
- `thresholds.memory_percent`
- `thresholds.disk_percent`
- `config_warnings`
- `active_targets`
- `excluded_targets`
- `target_warnings`

예시 응답:

```json
{
  "enabled": true,
  "interval_seconds": 30,
  "discord_webhook_configured": false,
  "monitor_auth_configured": true,
  "api_docs_enabled": false,
  "thresholds": {
    "memory_percent": 80,
    "disk_percent": 80
  },
  "config_warnings": [],
  "last_check": "2026-07-19T10:15:00"
}
```

이렇게 하면 모니터가 정상처럼 보여도, 실제로는 사용자가 의도한 설정인지 아니면 기본값으로 대체된 결과인지 구분하기 쉬워집니다.

특히 제외 대상 정보를 같이 보여주는 이유는, 운영자가 "보이지 않는 상태"를 모르고 정상 판단을 내려서는 안 되기 때문입니다.

### 3. 점검 대상 제외 규칙 추가

이제 특정 점검 대상은 설정으로 제외할 수 있습니다.

```env
MONITORING_EXCLUDED_TARGETS=demo_notes
```

이 방식은 다음 상황에 유용합니다.

- 아직 운영 범위에 넣지 않은 부가 서비스
- 임시 점검 제외가 필요한 대상
- 개발/테스트 환경에서 일부 연결을 의도적으로 비활성화한 경우

제외된 대상은 단순히 조용히 빠지는 것이 아니라, 운영 상태 응답과 대시보드에서 함께 드러나도록 했습니다.

### 4. 대시보드에서 상태의 이유를 함께 표시

대시보드는 이제 아래 정보를 함께 보여줍니다.

- 모니터링 주기를 반영한 자동 갱신 안내
- 메모리/디스크 경고 임계치
- 설정 상태 카드
- 설정 경고 표시
- 서비스별 연결 상태
- 문자열 `innerHTML` 의존도를 줄인 더 안전한 알림 렌더링

범위는 일부러 크게 넓히지 않았습니다. 새로운 관리자 시스템이나 프론트엔드 프레임워크를 붙인 것이 아니라, 현재 운영 화면을 더 신뢰할 수 있게 만드는 수준으로 제한했습니다.

### 5. 실행 단위 리포트 추가

이제 모니터링 루프는 1회 실행이 끝날 때마다 실행 단위 리포트를 남깁니다.

저장 항목 예시:

- 실행 ID
- 시작 시각 / 종료 시각
- 활성 점검 대상
- 제외된 점검 대상
- 대상 경고
- 서비스 상태 요약
- 자원 상태 요약
- 해당 실행에서 발생한 이벤트

저장 위치:

- `logs/runs/YYYY-MM-DD.jsonl`
- `logs/run-reports/YYYY-MM-DD.md`

이 기능을 추가한 이유는 이벤트가 하나도 없어도 점검이 수행되었다는 사실과 범위를 복기할 수 있어야 하기 때문입니다.

### 6. 데모 메모 서비스 상태 연동

`GET /health`는 이제 기본 DB 상태뿐 아니라 `demo_notes` 상태도 함께 반환합니다.

대시보드에서는 이 값을 이용해 다음을 빠르게 확인할 수 있습니다.

- 메모 서비스가 아예 비활성화된 상태인지
- URL 설정은 되어 있지만 실제 연결이 실패하는지
- 연결이 정상인지

즉, 대시보드가 단순 디자인 결과물이 아니라 실제 운영 중인 부가 서비스를 감시하는 화면 역할도 맡도록 범위를 넓혔습니다.

또한 `demo-notes` 페이지 자체는 목록 데이터가 비어 있어도 열려야 하며, DB 연결이 실패하더라도 완전히 빈 응답으로 끝나지 않도록 정리했습니다.

현재 화면 기준은 다음과 같습니다.

- 저장된 메모가 없으면 빈 상태 안내 표시
- 메모 저장소 연결이 실패하면 오류 안내 표시
- 루트 페이지 `/` 자체는 가능한 한 응답 유지

## 권장 점검 항목

`.env`를 변경한 뒤에는 아래 세 가지를 같이 확인하는 것이 좋습니다.

1. `GET /monitoring/status`에서 interval과 thresholds가 예상한 값으로 보이는지 확인
2. `excluded_targets`, `active_targets`, `target_warnings`가 의도한 값인지 확인
3. `/dashboard`에서 설정 상태와 설정 경고가 올바르게 보이는지 확인
4. `/health`에서 `demo_notes.status`가 의도한 값으로 보이는지 확인
5. 테스트 목적이 아니라면 `config_warnings`가 비어 있는지 확인
6. `logs/run-reports`에 실행 단위 리포트가 생성되는지 확인

## 메모

- 기본값 대체 동작은 애플리케이션을 계속 띄우기 위한 장치이지, 잘못된 설정을 숨기기 위한 장치가 아닙니다.
- 대시보드에 경고가 보이면 나중으로 미루지 말고 설정 부채로 보고 정리하는 편이 좋습니다.
- 허용 범위는 모니터링 루프가 지나치게 시끄러워지거나 너무 둔감해지지 않도록 보수적으로 잡았습니다.
- 제외 대상 규칙은 편의 기능이지만, 운영 범위를 흐리지 않도록 항상 상태 응답과 리포트에서 함께 확인하는 것이 좋습니다.

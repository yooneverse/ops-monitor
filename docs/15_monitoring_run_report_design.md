# 실행 단위 리포트와 예외 규칙 설계

## 1. 문서 목적

이 문서는 왜 점검 대상을 추상화했고, 왜 이벤트 로그와 별도로 실행 단위 리포트를 추가했으며, 왜 예외 규칙을 설정 기반으로 풀었는지를 설명한다.

이 문서를 따로 둔 이유는 기능 설명만으로는 설계 의도가 잘 보이지 않기 때문이다.

---

## 2. 배경

초기 구조에서는 DB와 부가 서비스를 개별 코드로 점검해도 동작에는 문제가 없었다.  
하지만 운영 도구로 확장하려면 세 가지 한계가 있었다.

### 2.1 점검 대상이 늘어날수록 분기 코드가 늘어남

- DB
- 부가 서비스
- 캐시
- 외부 API
- 업스트림 WAS

이런 대상이 늘어날수록 `if target == ...` 형태의 코드가 커질 수밖에 없다.

### 2.2 이벤트만으로는 점검 실행 맥락이 부족함

장애 이벤트가 없어도 점검은 수행되었을 수 있다.  
반대로 예외 규칙으로 어떤 대상을 뺐다면, 그 사실이 이벤트 이력에는 남지 않을 수 있다.

### 2.3 운영 중 임시 제외가 필요함

실제 운영에서는 특정 부가 서비스가 점검 범위에서 잠시 빠져야 할 수 있다.

예:

- 준비 중인 기능
- 임시로 꺼 둔 부가 서비스
- 현재 운영 책임 범위에서 제외된 대상

---

## 3. 점검 대상 추상화 설계

### 3.1 기본 단위

점검 대상은 아래 정보를 가진 구조체로 본다.

- 대상 키
- 상태 수집 함수
- 기대 상태
- 장애 메시지
- 복구 메시지
- 무시할 상태

이렇게 두면 대상마다 코드 패턴을 새로 만들지 않아도 된다.

### 3.2 왜 이 구조를 골랐는가

가능한 방법은 여러 가지였다.

- 상속 기반 클래스 구조
- 딕셔너리 기반 설정 구조
- 데코레이터 등록 방식

이번 프로젝트는 단순성과 가독성을 우선해서 dataclass 기반 레지스트리를 선택했다.

선택 이유:

1. Python 표준 구조로 이해하기 쉽다.
2. 테스트에서 가짜 타깃을 만들기 쉽다.
3. 확장 포인트가 명확하다.
4. 작은 운영 도구에 과한 추상화를 도입하지 않아도 된다.

## 4. 예외 규칙 설계

현재 예외 규칙은 `MONITORING_EXCLUDED_TARGETS`로 제공한다.

예:

```env
MONITORING_EXCLUDED_TARGETS=demo_notes
```

### 4.1 왜 환경변수로 풀었는가

운영 도구에서 예외 규칙은 코드 수정 없이 적용 가능한 편이 좋다.

환경변수 방식을 택한 이유는 아래와 같다.

- Docker Compose와 자연스럽게 연결된다.
- 배포 없이 설정만 바꿔 적용할 수 있다.
- 현재 프로젝트 규모에서 별도 DB 테이블까지 두지 않아도 된다.

### 4.2 왜 대시보드와 상태 API에 함께 노출하는가

예외 규칙은 "설정"일 뿐 아니라 "운영 맥락"이다.  
운영자가 지금 무엇을 보고 있지 않은지 알아야 판단 실수가 줄어든다.

그래서 아래 정보를 `/monitoring/status`에 포함한다.

- `active_targets`
- `excluded_targets`
- `target_warnings`

## 5. 실행 단위 리포트 설계

### 5.1 이벤트 로그와의 차이

| 항목 | 이벤트 로그 | 실행 단위 리포트 |
|---|---|---|
| 목적 | 장애/복구/경고 기록 | 점검 1회 전체 결과 기록 |
| 생성 조건 | 이벤트 발생 시 | 매 실행마다 |
| 주요 관심사 | 변화 | 범위와 맥락 |

### 5.2 포함 정보

실행 단위 리포트에는 아래 정보를 담는다.

- `run_id`
- 시작 시각 / 종료 시각
- 전체 상태
- 활성 점검 대상
- 제외된 점검 대상
- 대상 관련 경고
- 서비스별 상태
- 자원 사용량 요약
- 실행 중 생성된 이벤트 목록

### 5.3 저장 형식

두 가지 형식을 함께 저장한다.

| 경로 | 형식 | 이유 |
|---|---|---|
| `logs/runs/YYYY-MM-DD.jsonl` | 구조화 데이터 | 후처리, 검색, 자동 분석에 유리 |
| `logs/run-reports/YYYY-MM-DD.md` | 사람이 읽는 요약 | 운영 복기와 제출 문서 확인이 쉬움 |

### 5.4 왜 JSONL과 Markdown을 같이 두는가

한 가지 형식만 쓰는 것도 가능했다.

- JSONL만 쓰면 자동 처리에는 좋지만 사람이 바로 읽기 어렵다.
- Markdown만 쓰면 보기 쉽지만 후처리와 비교가 불편하다.

그래서 운영성과 활용성을 같이 가져가기 위해 둘 다 저장하도록 했다.

---

## 6. 기대 효과

이 설계를 통해 기대하는 효과는 아래와 같다.

- 체크 대상이 늘어나도 구조가 덜 흔들린다.
- 운영자가 점검 제외 대상을 놓치지 않는다.
- 장애가 없던 실행도 운영 기록으로 남는다.
- 면접과 포트폴리오에서 단순 모니터링을 넘는 설계 사고를 설명할 수 있다.

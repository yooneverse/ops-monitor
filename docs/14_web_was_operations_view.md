# WEB/WAS 운영 관점 정리

## 1. 문서 목적

이 문서는 Ops Monitor를 단순한 개발 연습 프로젝트가 아니라, WEB/WAS 운영자가 어떤 문제를 어떻게 다루려 했는지 설명하기 위해 작성한다.

면접, 포트폴리오, 기술 설명 자리에서 아래 질문에 답하기 쉽게 만드는 것이 목적이다.

- 왜 이런 기능이 필요한가
- 왜 이런 구조를 선택했는가
- 운영자 관점에서 어떤 가치가 있는가

---

## 2. 이 프로젝트를 운영 도구로 보는 이유

### 2.1 단순 상태 조회를 넘는 지점

Ops Monitor는 다음 요소를 함께 다룬다.

- 공개 프로브와 보호된 운영 API의 분리
- 준비 상태와 생존 상태의 분리
- 전이 기반 이벤트 감지
- 실행 단위 리포트 저장
- 운영 액션 추적

즉, 단지 "앱이 살아 있나"를 보여주는 게 아니라, 운영자가 실제로 점검하고 조치하고 복기하는 흐름을 염두에 두고 있다.

### 2.2 WEB/WAS 운영에서 중요한 이유

WEB/WAS 운영은 대개 아래 질문으로 압축된다.

- 애플리케이션 프로세스는 살아 있는가
- 업스트림과 저장소 연결은 정상인가
- 지금 트래픽을 받아도 되는가
- 장애는 진행 중인가, 방금 복구되었는가
- 누가 어떤 조치를 했는가

Ops Monitor는 바로 이 질문들에 대응하기 위해 설계되었다.

---

## 3. 운영 포인트별 설명

### 3.1 `livez`와 `readyz` 분리

운영 관점에서 가장 기본이지만 중요한 부분이다.

- `livez`: 프로세스 생존 확인
- `readyz`: 실제 서비스 준비 확인

이 둘을 분리한 이유는, 프로세스가 떠 있어도 DB 연결이 끊겨 있으면 실제 서비스는 준비되지 않은 상태일 수 있기 때문이다.

### 3.2 장애를 전이로 보는 이유

운영자는 동일한 장애가 100번 반복 기록되는 것보다 "정상에서 비정상으로 바뀐 시점"과 "비정상에서 정상으로 돌아온 시점"이 더 중요하다.

그래서 이 프로젝트는 아래에 집중한다.

- `connected -> disconnected`
- `disconnected -> connected`

이 접근은 알림 피로도를 줄이고, 복구 확인을 더 명확하게 만든다.

### 3.3 점검 대상 추상화

초기에는 DB와 부가 서비스 정도만 보면 충분할 수 있다.  
하지만 운영 도구는 계속 확장된다.

- 캐시
- 외부 API
- 업스트림 노드
- 워커 프로세스

그래서 점검 대상을 처음부터 레지스트리 형태로 다루는 것이 WEB/WAS 운영 도구답다고 판단했다.

### 3.4 실행 단위 리포트

장애 이벤트만 보면 점검이 수행되었는지, 특정 대상을 빼고 돌렸는지 알기 어렵다.  
운영 관점에서는 "점검 1회" 자체도 기록 단위가 된다.

이 프로젝트가 실행 단위 리포트를 추가한 이유는 다음과 같다.

- 어떤 점검 대상을 실제로 실행했는지 확인 가능
- 어떤 대상을 예외 규칙으로 제외했는지 확인 가능
- 이벤트가 없어도 점검 수행 사실을 남길 수 있음

### 3.5 운영 액션 추적

운영 API가 단지 조회만 한다면 영향 범위는 제한적이다.  
하지만 재시작 같은 액션이 들어가면 반드시 이력이 남아야 한다.

그래서 운영 액션은 아래를 함께 남긴다.

- 수행자
- 수행 시각
- 성공/실패 결과

이건 운영 감사성과 협업 신뢰성 측면에서 중요하다.

---

## 4. 면접에서 설명하기 좋은 포인트

### 4.1 한 문장 설명

Ops Monitor는 WEB/WAS 운영자가 생존 상태, 준비 상태, 점검 대상, 장애 전이, 운영 조치 이력을 한 흐름으로 다루기 위해 만든 경량 운영 모니터링 도구입니다.

### 4.2 기술적 강점

- 헬스 체크를 `livez`와 `readyz`로 분리했다.
- 상태값이 아니라 전이 기준으로 incident / recovery를 판단한다.
- 점검 대상을 레지스트리로 관리해 확장성을 확보했다.
- 실행 단위 리포트를 남겨 운영 복기성을 높였다.
- 운영 액션에 수행자와 결과를 함께 기록했다.

### 4.3 운영 관점 강점

- 조회와 조치 흐름이 분리되지 않고 한 시스템 안에 있다.
- 잘못된 설정도 기본값으로 복구하면서 경고를 남긴다.
- 대시보드가 단순한 시각화가 아니라 판단용 화면 역할을 한다.

---

## 5. 앞으로 운영 도구로 더 키운다면

우선순위는 아래 순서를 생각하고 있다.

1. 업스트림 체크 대상 추가
2. 예외 규칙 세분화
3. 실행 리포트 diff 비교
4. 운영 액션 확대

이 방향은 "운영자가 실제로 손이 가는 반복 점검을 얼마나 더 줄일 수 있는가"라는 기준으로 잡는다.
